# Live image-annotation API study

Explicit opt-in live `gpt-4o-mini` evaluation of the seven versioned image-annotation shell scripts, with annotations off. The original scripts and installed `llm==0.36` client run unchanged. No runtime command-specific optimizations are added.

The persistent user service `incr-image-annotation-api.service` waits until `incr-strengths-microbench-final.service` finishes, then acquires its measurement lock. It installs the client in this study's ignored private virtual environment, checks the five-image minimum sequence in all three modes once, then evaluates the historical ten-image paper recipe three times in native Bash, pinned original Incr and current Incr/Observe. The same bounded maintained harness records CPU, wall time, cache/disk statistics and per-invocation validation. Inputs are fingerprinted; runtime binaries and source are frozen by the runner. Native runs establish each repetition's references and incremental engine order alternates. The full run has 63 invocations, plus 21 minimum-validation invocations. Stop on failed validation; no automatic retries of failed sequences.

This is a live network/model workload, distinct from deterministic correctness evidence. Fixed seed and temperature do not guarantee identical generated titles. Exact output manifests are retained, but cross-mode validation compares image payload sets rather than generated filenames or duplicate counts. Independent checks require every input image's unchanged bytes to be represented in the output, valid output file types, nonempty titles and no API/client diagnostics. This does not prove identical title text, semantic title quality, or identical stochastic effects. Filename sanitization remains in the original scripts. Live latency, model drift and provider caching can influence speedups; do not pool these samples with deterministic application benchmarks.

Top-level `status.json` records queued/setup/minimum-validation/running/complete/failed. Detailed progress and evidence are in `results/minimum-01/` and `results/paper-01/`; `console.log` records the background runner. The original historical manifest remains unchanged and continues to exclude this opt-in workload. `manifest.json` here selects it explicitly through the maintained runner's study-root override. Its runner is frozen under `.work/queued-harness` at queue time.

Credentials are read from an isolated private temporary `llm` configuration outside Git; no secret is included in shell scripts, unit arguments, environment values, setup receipts or documentation. The service removes that temporary directory on exit. Re-launch requires new explicit credentials. The service survives editor/chat closure with user lingering enabled; it does not survive host shutdown or reboot.

Setup diagnostics are preserved separately: `minimum-01` stopped before timing because the service could not find Cargo; `minimum-02` exposed the inherited empty statistics directory and missing historical reporting reference; `minimum-03` passed all seven native Bash cases before exposing the isolated-client Python shadowing the compiler Python. `minimum-04` is the clean run after these fixes. The client directory is appended after the parser environment on PATH. These failed attempts are not pooled with final timings.

The corrected `minimum-04` cohort completed all **21/21** invocations successfully (seven scripts × three modes). `minimum-validation-checkpoint.json` saves its mode totals and frozen runtime fingerprints. The full three-repetition continuation is `paper-01`; consult its live status rather than inferring completion from this checkpoint.
